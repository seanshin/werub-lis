# 백업·복구 운영 절차서

> 환경: **AWS 서울(ap-northeast-2)** — EC2(앱) + RDS PostgreSQL(DB) + S3(백업)
> 단일 노드 구성이므로 **복구 속도와 손실 폭이 곧 가용성**이다. 이 문서는 그 목표를 달성·검증하는 절차다.
> 작성일 2026-07-21

## 0. 목표 (승인 필요 — 설계 §10 D3)

| 지표 | 목표 | 의미 |
|---|---|---|
| **RPO** | 5분 | 장애 시 허용 데이터 손실 — **RDS 자동백업·PITR**로 달성 |
| **RTO** | 1시간 | 장애 인지부터 진료 재개까지 — 리허설로 **실측**해 검증 |

> 목표는 선언이 아니라 측정 대상이다. 분기 리허설에서 실제 소요시간을 기록하고, 목표를 넘으면
> 절차를 고치거나 목표를 현실화한다.

## 1. 백업 계층 (AWS 서울)

| 계층 | 대상 | 주기 | 보관 | 수단 |
|---|---|---|---|---|
| L1 **RDS 자동백업 + PITR** | DB 전체·트랜잭션 로그 | 연속 | 14일 | **RDS 기능**(§2) |
| L2 논리 백업 | `pg_dump` → **S3** | 일 1회 03:00 | 30~90일 | `backup.sh` + GPG(§3) |
| L3 장기 스냅샷 | RDS 수동 스냅샷 | 월 1회 등 | 정책에 따라 | AWS Backup |
| L4 앱 서버 | AMI(골든 이미지) | 변경 시 | 최근 2~3개 | EC2 |

> **AWS로 오면서 달라진 점** — 개발 서버에서 직접 구성해야 했던 WAL 아카이빙(선행과제 S2)은
> **RDS 자동백업이 대체**한다. 자동백업을 켜는 순간 PITR이 가능해진다.
> 대신 **L2(논리 백업 → S3)는 여전히 필요**하다. RDS 스냅샷은 AWS에 종속되므로,
> 사업자와 무관하게 열 수 있는 사본을 별도로 갖는다.

**⚠ 전 계층 리전 고정**: RDS 백업·S3 버킷·AWS Backup 볼트 모두 **ap-northeast-2**.
교차 리전 복제는 국내 보관 요건에 걸린다(설계 §1).

## 2. RDS 자동백업 · PITR

> 공용 서버에서 설정 변경이 불가해 보류됐던 체크리스트 **C2 잔여**가 여기서 해소된다.

### 2-1. 설정 (RDS 콘솔/CLI)

| 항목 | 값 | 이유 |
|---|---|---|
| 자동백업 보존 | **14일** | PITR 가능 범위 = 보존 기간 |
| 백업 창 | 새벽(예: 17:00~18:00 UTC = 02:00~03:00 KST) | 진료 영향 최소 |
| 유지관리 창 | 진료 영향 적은 시간 | 마이너 패치 자동 적용 시각 |
| 저장 암호화 | **활성(KMS)** | 생성 후 변경 불가 — 처음에 반드시 켤 것 |
| 삭제 방지 | 활성 | 실수 삭제 차단 |
| 로그 내보내기 | postgresql 로그 → CloudWatch | 장애 조사 |

```bash
aws rds modify-db-instance --db-instance-identifier lis-prod \
  --backup-retention-period 14 --apply-immediately --region ap-northeast-2
```

### 2-2. 검증

```bash
# 최근 복구 가능 시점이 5분 이내로 유지되는지 = RPO 실측
aws rds describe-db-instances --db-instance-identifier lis-prod --region ap-northeast-2 \
  --query "DBInstances[0].LatestRestorableTime"
```
이 값이 현재 시각에서 크게 뒤처지면 RPO 목표를 못 지키는 상태다. **CloudWatch 알람으로 감시**.

### 2-3. PITR 복구

```bash
# 지정 시점으로 새 인스턴스 생성(원본은 건드리지 않는다)
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier lis-prod \
  --target-db-instance-identifier lis-restore-$(date +%Y%m%d%H%M) \
  --restore-time 2026-07-21T09:15:00Z \
  --db-subnet-group-name lis-db-subnets --vpc-security-group-ids <sg-lis-db> \
  --region ap-northeast-2
```
복원본으로 먼저 **데이터가 기대한 시점이 맞는지 확인**한 뒤, 앱의 `DATABASE_URL`을 전환한다.
원본을 직접 되돌리지 않으므로 판단 오류 시 되돌릴 수 있다.

**용도**: 잘못된 대량 삭제·오조작을 사고 직전으로 되돌릴 때.

<details><summary>참고 — 자체 관리 PostgreSQL을 쓸 경우의 WAL 아카이빙 설정(현 개발 서버 방식)</summary>

### 설정

`postgresql.conf` (컨테이너면 command 인자 또는 마운트한 conf):
```
wal_level = replica
archive_mode = on
archive_command = '/archive/wal-push.sh %p %f'
archive_timeout = 300          # 5분 — RPO 목표와 직결(트래픽이 없어도 5분마다 세그먼트 마감)
max_wal_size = 2GB
```

`archive_command`는 실패 시 0이 아닌 값을 반환해야 한다(그래야 PostgreSQL이 재시도하고 WAL을 보존한다).
스크립트 예시:
```bash
#!/usr/bin/env bash
# /archive/wal-push.sh <경로> <파일명> — 오브젝트 스토리지로 업로드. 실패 시 비0 종료.
set -euo pipefail
SRC="$1"; NAME="$2"
gpg --batch --yes --trust-model always -r "$LIS_BACKUP_GPG_RECIPIENT" -o "/tmp/$NAME.gpg" -e "$SRC"
rclone copyto "/tmp/$NAME.gpg" "$LIS_WAL_ARCHIVE/$NAME.gpg"   # 또는 aws s3 cp
rm -f "/tmp/$NAME.gpg"
```

### 2-2. 검증 (구성 직후 반드시)

```sql
-- 아카이빙이 실제로 돌고 실패가 없는지
SELECT archived_count, last_archived_wal, last_archived_time, failed_count, last_failed_wal
FROM pg_stat_archiver;
```
`failed_count`가 증가하면 **디스크에 WAL이 쌓여 결국 DB가 멈춘다.** 모니터링 알림에 반드시 포함할 것.

### 2-3. PITR 복구 (특정 시점으로)

```bash
# 1) 기준 백업 복원(베이스 백업 또는 최근 pg_dump 이후라면 §4 논리 복구 사용)
# 2) recovery 설정
#    restore_command = '/archive/wal-fetch.sh %f %p'
#    recovery_target_time = '2026-07-21 09:15:00+09'
# 3) 기동 → 목표 시점까지 재생 → promote
```

## 3. 논리 백업 → S3 · 암호화 (선행과제 S1)

`infra/docker/.env` 또는 크론 환경에 지정하면 `backup.sh`가 자동 처리한다.

| 변수 | 값 | 효과 |
|---|---|---|
| `LIS_BACKUP_DIR` | 기본 `/home/<계정>/backups/lis` | 로컬 보관 경로(0700) |
| `LIS_BACKUP_KEEP_DAYS` | 기본 14 | 로컬 순환 |
| `LIS_BACKUP_GPG_RECIPIENT` | GPG 공개키 ID | **설정 시 암호화 후 평문 원본 삭제** |
| `LIS_BACKUP_OFFSITE` | `s3://lis-prod-backup/db/` 또는 마운트 경로 | 사본 전송(S3 CLI/rclone) |
| `LIS_BACKUP_RSYNC_OPTS` | (선택) | 추가 옵션 |

**GPG 키 운용**
```bash
gpg --full-generate-key                       # 백업 전용 키쌍
gpg --export -a "lis-backup" > lis-backup.pub
# ⚠ 개인키는 서버에 두지 않는다. 복구 담당자만 오프라인 보관(금고·별도 매체).
#    개인키를 잃으면 백업을 영원히 못 연다 — 키 백업 절차를 별도 문서화할 것.
```

**S3 버킷 요건**
- 리전 **ap-northeast-2**, 퍼블릭 액세스 차단 전면 ON, **기본 암호화(KMS)**
- 버전 관리 ON, 수명주기(예: 90일 후 Glacier, 1년 후 만료)
- **교차 리전 복제 금지**(국내 보관 요건)
- EC2 인스턴스 프로파일에 **이 버킷만** 권한 부여

**크론**
```
0 3 * * * /srv/lis/infra/scripts/backup.sh >> /srv/lis/backup.log 2>&1
```

**검증**
```bash
ls -l "$LIS_BACKUP_DIR" | head          # 최신 파일 0600, 디렉터리 0700
# 오프사이트에 같은 파일이 도착했는지 원격에서 확인
# 복호화 시험: gpg -d <파일>.gpg | gunzip | head -5
```

## 4. 복구 절차 (장애 유형별)

### 4-1. EC2(앱 서버) 장애

**DB는 RDS에 있으므로 데이터 손실이 없다.** 앱 서버만 재생성한다.

```
1. AMI에서 새 인스턴스 기동(같은 SG·서브넷·인스턴스 프로파일)
2. Elastic IP 재연결        ← Cloudflare 설정 변경 불필요
3. Secrets Manager에서 .env 렌더링
4. docker compose up -d → 스모크(구축절차서 §10)
```
목표 30분 이내. AMI를 최신으로 유지할수록 빨라진다.

### 4-2. RDS 장애

```
1. 스냅샷 또는 PITR로 새 인스턴스 복원(§2-3)
2. 앱 .env의 DATABASE_URL을 새 엔드포인트로 교체 → api 재기동
3. 스모크 + 감사 체인 무결성 확인(§4-5)
```

### 4-3. 계정·리전 수준 장애 / 논리 백업에서 복구

```
1. 인스턴스·RDS 재생성       → docs/실서비스_구축절차서.md §2~§4
2. .env 복원(Secrets Manager 또는 보관처)
3. S3에서 최신 논리 백업 취득 → 복호화
4. DB 복원(§4-4)
5. 컨테이너 기동 → 마이그레이션 → 스모크
6. Cloudflare 오리진 전환
```
소요 목표 1시간. **병목은 대개 3~4단계**이므로 리허설에서 이 구간을 실측한다.

### 4-4. 데이터 오조작 (잘못된 삭제·대량 갱신)

PITR로 사고 직전 시점 복구(§2-3). 운영 DB를 직접 되돌리지 말고 **복원본을 먼저 확인**한 뒤 전환한다.

### 4-4b. 논리 백업 복원 명령

```bash
gpg -d lis-YYYYMMDD-HHMMSS.sql.gz.gpg > /tmp/lis.sql.gz    # 암호화본인 경우
gunzip -c /tmp/lis.sql.gz | psql "postgresql://<user>:<pw>@<rds-endpoint>:5432/lis?sslmode=require"
rm -f /tmp/lis.sql.gz          # 평문 중간산출물 즉시 삭제
```

> ⚠ 운영 DB에 직접 붓기 전에 **기존 DB를 반드시 먼저 백업**한다. 되돌릴 수 없는 작업이다.

### 4-5. 복구 후 필수 확인

```bash
curl -s https://<도메인>/api/v1/health                       # db: up
# 감사 체인 무결성 — 복원본이 훼손되지 않았는지
curl -s -H "Authorization: Bearer $TOK" https://<도메인>/api/v1/audit/verify
# → {"ok":true, "brokenAt":null}
```
감사 체인이 깨져 있으면 **복원본이 불완전하거나 중간 구간이 유실**된 것이다. 다른 백업본으로 재시도.

## 6. 모니터링 연동

아래는 **알림이 없으면 조용히 실패**하는 항목이다. 반드시 `OPS_WEBHOOK_URL` 알림에 포함한다.

| 항목 | 위험 | 확인 방법 |
|---|---|---|
| **PITR 지연** | RPO 미달 | RDS `LatestRestorableTime`이 현재에서 크게 뒤처짐 → CloudWatch 알람 |
| RDS 스토리지 여유 | 소진 시 **DB 정지** | CloudWatch `FreeStorageSpace` |
| RDS CPU·연결수 | 성능 저하 | `CPUUtilization`, `DatabaseConnections` |
| 백업 크론 미실행 | 논리 백업 공백 | 최신 S3 객체 mtime > 26시간 |
| S3 업로드 실패 | 사업자 종속 사본 없음 | `backup.sh` 로그·알림 |
| EC2 디스크·메모리 | 70·80% 초과 | CloudWatch Agent |
| 인증서 만료 | 서비스 중단 | 만료 30일 전 알림 |

## 7. 보존기간 (법정)

`apps/api/src/domain/retention.ts`가 정본이다.

| 데이터 | 보존 | 자동 정리 |
|---|---|---|
| 검사결과 | 3,650일(10년) | **불가**(`purgeable: false`) — 법정 보존 |
| 감사로그 | 1,095일(3년) | 가능 — 개인정보보호법 시행령 §30(민감정보 2년) 상회 |
| 연계로그 | 365일 | 가능 |
| 알림 | 365일 | 가능 |

자동 정리 크론은 `LIFECYCLE_PURGE=on`일 때만 동작한다. **법무 확정 전까지 미설정(=미실행) 유지**.
정리는 감사 체인의 연속 prefix만 지우므로 무결성 검증과 충돌하지 않는다.
