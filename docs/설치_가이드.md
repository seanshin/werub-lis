# LIS 설치 가이드 (사이트 단위)

작성 2026-07-30 · 기준 릴리즈 **v1.56.0**

> **배포 형태: 사이트 = 서버 = DB (1:1:1).** 한 병원(사이트)에 한 벌씩 단독 설치한다.
> 멀티테넌트가 아니며, 사이트끼리 DB·백업·업그레이드 시점을 공유하지 않는다.

## 1. 사전 조건

| # | 항목 | 확인 방법 |
|---|---|---|
| H1 | Linux 호스트, **Docker + compose v2** | `docker compose version` |
| H2 | 디스크 여유 **10GB 이상**(이미지·DB·백업 별도) | `df -h` |

## 2. 설치

```bash
git clone <리포지토리> /srv/lis && cd /srv/lis

# 운영 설치 — 데모 데이터 없음
./infra/install/install.sh --site-code SEOUL-A --origin https://lis.hospital.kr

# 평가·교육용 — 합성 데모 데이터 포함(운영 설치에는 쓰지 말 것)
./infra/install/install.sh --site-code DEMO --origin https://demo.example.kr --with-demo
```

| 인자 | 설명 |
|---|---|
| `--site-code` | 사이트 식별자(영숫자·`-`·`_`, 2~32자). **승인 기록·준비도 내보내기에 결속**된다 |
| `--origin` | 서비스 도메인. **https 필수** — 환자 식별정보가 오가므로 http는 거부한다 |
| `--trust-proxy-hops` | 앞단 프록시 수(기본 1). Cloudflare+nginx면 **2** |
| `--with-demo` | 합성 데모 데이터 포함 |
| `--no-backup-cron` | 백업 스케줄을 외부(시스템 스케줄러)에서 관리할 때만 |

스크립트가 하는 일: 사전점검 → `.env` 생성(**시크릿 무작위 생성**) → 이미지 빌드 → DB·API 기동 → 마이그레이션 적용 확인 → 초기 데이터 → web 기동 → **백업 cron 등록**(매일 03:00, 멱등) → 설치 검증 → **관리자 초기 비밀번호 1회 출력**.

### 안전 장치 (설치가 중단되는 경우)

| 상황 | 동작 | 이유 |
|---|---|---|
| `.env`가 이미 있다 | **중단** | 덮어쓰면 기존 DB 접근 불가(비가역). 재설치 시 기존 `.env`를 보관 후 옮길 것 |
| DB에 사용자가 이미 있다 | **시드 건너뜀** | 재설치가 데이터를 지우지 않게 |
| 포트 점유·디스크 부족 | 중단 | — |
| `--origin`이 http | 중단 | 환자 정보 평문 전송 방지 |

> **시크릿은 설치 때마다 새로 만든다.** 패키지에 고정 기본값을 넣지 않는 것이 원칙이다 —
> 한 사이트가 유출되면 전 사이트가 뚫리기 때문이다. `DB_PASSWORD`·`JWT_SECRET`·
> `CRITICAL_WEBHOOK_SECRET`이 자동 생성된다.
>
> ⚠ **`.env`를 잃으면 DB를 열 수 없다.** 설치 직후 안전한 곳에 보관할 것.

## 3. 초기 데이터 — 무엇이 깔리나

`SEED_PROFILE`로 나뉜다. 설치 스크립트가 자동 선택하지만, 수동 실행도 가능하다.

| 프로파일 | 내용 | 개시 후 |
|---|---|---|
| **starter**(기본) | 역할 10 · **관리자 U00 1개** · 컨테이너 · 검사 마스터 51 · 참고치 45 · 코드매핑 · QC 목표 21 · 서명 대기값 | **남는다** |
| **demo**(`--with-demo`) | 직무 계정 U01~U07 · 환자 16 · 오더 15 · 검체 · 배양 · 병리 · 수혈 · 유전체 | **개시 전 전량 삭제** |

```bash
# 수동 실행(설치 후 데모만 추가 등)
SEED_PROFILE=starter npm --prefix apps/api run seed
SEED_PROFILE=demo    npm --prefix apps/api run seed
SEED_PROFILE=all     npm --prefix apps/api run seed   # 기본값
```

> **운영 설치에 데모를 넣지 말 것.** 데모 계정은 개시 전 폐기 대상(체크리스트 B1)이라,
> 지금 넣으면 나중에 지워야 할 일을 만들어 두는 것이다. 화면 확인이 목적이면 별도 평가 사이트에 설치한다.
>
> **마스터는 전부 대표값이다.** 참고치·QC 목표는 검사실 서명으로 실값 교체해야 한다(`/admin/signoff`).

## 3-1. 시드 정리 — 개시 전 데모 데이터 제거

시드가 만든 행은 **생성 시점에 `seed_artifact`에 등록**된다. 그래서 배치 단위로 **선택 삭제**가 가능하고, 실 데이터는 애초에 대상이 되지 않는다.

```
GET  /api/v1/admin/seed-cleanup/real-data           실 환자 데이터 존재 여부
GET  /api/v1/admin/seed-cleanup/preview?batch=…     엔티티별 건수·차단여부·확인문구(읽기전용)
POST /api/v1/admin/seed-cleanup/request             ① 요청 {batch, confirmPhrase} — 실행하지 않는다
POST /api/v1/admin/seed-cleanup/approve/:runId      ② 승인·실행 — **승인자 본인 토큰**으로 호출
```

| 배치 | 정리 대상 |
|---|---|
| `product-demo` · `site-pilot` · `e2e` | ✅ 삭제 가능 |
| `site-starter` | ❌ **보존**(마스터 — 서명 실값으로 교체될 뿐) |

**안전장치** — 셋 다 서버가 강제한다(화면 우회 불가).

1. **실 환자 데이터가 하나라도 있으면 409로 거부**한다. override 수단이 없다(요청·승인 양쪽에서 판정).
2. `preview`가 준 **확인 문구가 정확히 일치**해야 요청이 등록된다(`product-demo 162건 삭제`).
3. **다른 관리자가 자기 계정으로 로그인해 승인**해야 실행된다 — 승인자 ID를 대신 입력하는 방식이 아니다(30분 만료).
4. 시작·완료·차단 시도가 **감사 체인과 실행 이력**에 남는다.
5. 마스터·계정(`provider`·`appUser` 등)은 **배치에 등록돼 있어도 삭제하지 않는다** — 지우면 FK가 `SET NULL`이라 병리 서명자·결과 검증자가 조용히 사라진다. 계정 폐기는 `/admin/users` 소관.

실측(격리 DB): 데모 162건 전량 삭제 → 환자·오더·결과·데모계정 0, starter 마스터(검사 51·참고치 45·관리자 1·역할 10) 보존.

> ⚠ **추적 이전에 만들어진 데이터는 정리 대상이 아니다.** 현 파일럿 서버처럼 등록 없이 쌓인
> 데이터는 API가 "실 데이터"로 보아 차단한다(fail-safe). 그 경우 `infra/scripts/pilot-cleanup.sql`
> (폴백 유지)을 쓰거나 백필이 필요하다. **신규 사이트는 설치 시점부터 추적되므로 해당 없다.**

## 4. 설치 검증

설치 스크립트가 마지막에 자동 실행하며, 이후에도 단독으로 돌릴 수 있다(읽기 전용).

```bash
./infra/install/verify.sh
```

확인 항목 — **"떴다"가 아니라 "쓸 수 있다"** 를 본다.

| 구분 | 항목 |
|---|---|
| 기동 | 컨테이너 3종 · health 200 · web 200 |
| 보안 | 주요 API **무인증 401** · Swagger 비노출 · `.env` 권한 600 · 시크릿 길이(값 미출력) |
| 데이터 | 스키마 50+ 테이블 · 역할 10 · 관리자 1+ · 검사 마스터 1+ |

마지막에 **개시 전 잔여**를 안내한다(실패가 아니다) — 위험치 채널 미설정 또는 시드 sink, 데모 계정 활성 여부.

## 5. 설치 직후 할 일

설치는 **개시가 아니다.** 아래는 개시 전에 사람이 해야 한다.

| 순서 | 할 일 | 화면 |
|---|---|---|
| 1 | 관리자 비밀번호 변경(초기값은 설치 시 1회 출력) | 로그인 후 |
| 2 | 실 직원 계정 생성·역할 배정 | `/admin/users` |
| 3 | **위험치 통보 채널 URL 입력 + 테스트 발송** | `/admin/settings` |
| 4 | 검사실 실값 서명(참고치·QC·EDI) | `/admin/signoff` |
| 5 | 조직 결재 기입 | `/admin/gates` |
| 6 | 개시 준비도 확인 | `/admin/console` |

**이 스크립트 범위 밖(반드시 별도 구성)**

- **TLS·도메인·리버스 프록시** — `docs/실서비스_구축절차서.md` §8
- **오프사이트 백업 경로**(`LIS_BACKUP_OFFSITE`) — cron은 설치가 등록하지만 **경로는 비어 있다.**
  로컬 보관만으로는 호스트 소실에 무방비다. 값 확정 후 `.env`에 넣을 것.
  그리고 `infra/scripts/restore-rehearsal.sh`로 **복원 검증**까지 할 것 —
  "백업이 있다"와 "복원된다"는 다른 문제다.
- **연계 자격증명**(HIS·PACS) — 조직 결재(A-3) 후 주입

## 6. 자주 겪는 문제

| 증상 | 원인·조치 |
|---|---|
| `포트 4101 사용 중` | 같은 호스트에 이미 LIS가 있거나 다른 서비스가 점유. **1 사이트 = 1 서버**가 원칙이므로 호스트를 분리할 것 |
| `.env가 이미 있다` | 재설치다. 기존 `.env`를 보관·이동한 뒤 재실행. 그냥 지우면 **기존 DB를 열 수 없다** |
| 마이그레이션 로그 없음 | `docker logs lis-api` 확인. 스키마 변경 배포 시 `--no-cache` 빌드 필요 |
| 기존 데이터 감지로 시드 건너뜀 | 정상. 빈 상태에서 시드하려면 **의도적으로** DB를 비운 뒤 재실행 |
| 설치 후 로그인 불가 | `verify.sh`의 "관리자 계정" 항목 확인. 0이면 시드 미실행 |

## 7. 업그레이드

사이트마다 **독립적으로** 올린다(사이트마다 다른 버전이 정상 상태다).

```bash
cd /srv/lis && git fetch && git checkout <태그>
docker compose -p lis --env-file infra/docker/.env -f infra/docker/docker-compose.prod.yml \
  build --no-cache api web
docker compose -p lis --env-file infra/docker/.env -f infra/docker/docker-compose.prod.yml up -d
./infra/install/verify.sh
```

> ⚠ **스키마 변경이 있으면 `--no-cache` 필수.** 캐시 빌드가 소스 변경을 무시하고 옛 이미지를
> 배포한 사고가 있었다(v1.35.0). 배포 후 `docker exec lis-api grep version package.json`으로
> **러닝 이미지의 코드 버전**을 확인할 것 — 헬스 200만으로 배포 성공을 단정하지 않는다.
>
> 업그레이드 전 **백업**은 필수다. 마이그레이션은 되돌리기 어렵다.
