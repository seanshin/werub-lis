# 운영 관리 콘솔 — 통합·워크플로우화 기획서 (수정·보완)

작성: LIS 구축팀 · 2026-07-25 · 기준 릴리즈 v1.10.0
대상: "관리 목적으로 **정의해야 하는** 항목"들을 다루는 관리 기능(현 13+ 화면 산재)을 **하나의 워크플로우 콘솔**로 정리.

> 목적: 개시 전·운영 중 **정의·설정·서명·승인해야 하는 항목**이 여러 화면에 흩어져 있어, 담당자가
> "무엇을·어디서·지금 어느 단계까지" 했는지 한눈에 못 본다. 이를 **정의→검증→승인/서명→반영→운영**
> 워크플로우로 모델링하고 **한 콘솔**로 모은다. (이미 `개시 준비도`·`서명·결재`가 부분 통합의 선례)

---

## 0. 구현 현황 (2026-07-25, v1.11.0)

✅ **P1~P3 전량 구현·배포** — `/admin/console`(운영 관리 콘솔).
- P1: 4축 15개 정의 항목 레지스트리·상태·다음행동 딥링크·개시차단 요약
- P2: 표준 lifecycle(UNDEFINED→…→LIVE+REVIEW)·워크플로우 파이프라인 뷰·재검토 통합
- P3: 통합 이력 타임라인(결재·서명·반입·설정·프로토콜, 시크릿 미노출)
- 중복 정리: signoff→gates·readiness→console 승격
이하는 그 근거가 된 원 기획.

## 1. 배경·문제 정의

이번까지 "사람 몫(외부 회신·조직 정의)"을 관리 기능으로 도출해 왔다(위험치 채널 설정·조직 결재
추적·서명 워크시트·코드셋 반입기·개시 준비도 등). 그 결과 **관리 기능은 충분히 갖춰졌으나 산재**한다.

핵심 문제:
- **진입점 다수** — 관리 그룹에 13개 화면(+마스터·청구·감사). "무엇을 정의해야 하는가"가 화면마다 흩어짐.
- **워크플로우 부재** — 각 항목이 `정의→검증→승인/서명→반영` 단계를 거치는데, 그 **단계·상태가 화면별로 제각각**(어떤 건 상태 없음, 어떤 건 결재 상태만, 어떤 건 대표값 표시만).
- **상태 가시성 부족** — `개시 준비도`가 일부를 집계하나(8개 항목), 실제 정의 항목은 훨씬 많고(참고치 47·QC 21·EDI·코드셋 6종·프로토콜 등) **드릴다운·다음행동 연결이 얕다**.
- **중복·이동** — `서명·결재`↔`서명 워크시트`, `마스터`↔`코드셋`↔`용어코드`처럼 겹치는 개념이 분산.

## 3. 문제점 진단

1. **정의 항목의 단일 레지스트리 부재** — "개시/운영에 정의가 필요한 것"의 마스터 목록이 없다. 준비도가 8개만 하드코딩.
2. **lifecycle 불일치** — 정의 항목마다 상태 표현이 달라, "지금 어느 단계"를 통일된 언어로 못 본다.
3. **다음 행동(next action) 연결 얕음** — 준비도가 링크는 걸지만, 항목별 "정의→검증→서명" 흐름을 이어주지 않는다.
4. **담당·이력 분산** — 결재 이력(gates)·서명(worksheet)·반입 이력(catalog_version)·설정 변경(system_setting.updatedBy)이 각기 저장. 통합 감사 뷰 없음.

## 4. 목표·원칙

- **한 콘솔** — 관리 정의 항목을 `운영 관리 콘솔` 한 곳에서 보고 진입. 개별 화면은 상세 편집기로 재사용(재작성 최소).
- **공통 워크플로우** — 모든 정의 항목을 하나의 lifecycle 상태머신으로 표준화.
- **드릴다운·다음행동** — 콘솔에서 항목 상태·담당·다음행동을 보고 해당 편집 화면으로 이동, 완료 시 상태 자동 갱신.
- **안전 원칙 유지** — 시드/대표값은 실 완료(OK)와 구별(SEED). 조직 결재·검사실 서명은 페이크 금지(정직한 대기).
- **비파괴** — 기존 화면·엔드포인트는 유지, 콘솔은 그 위의 집계·네비게이션 레이어.

## 5. 설계 제안

### 5.1 관리 항목 공통 워크플로우(lifecycle) 모델

모든 정의 항목을 아래 상태로 표준화한다:

```
UNDEFINED(미정의) → SEEDED(시드/대표값) → CONFIGURED(설정·입력됨)
      → VERIFIED(검증됨: 테스트발송·차이확인·dry-run) → SIGNED/APPROVED(서명·결재)
      → LIVE(반영·운영) → REVIEW(재검토 필요: 인력변경·정기만료·근거개정)
```

- 각 항목은 **owner(담당)·evidence(근거)·nextAction(다음행동)·fixHref(편집 화면)** 를 가진다.
- 상태는 **가능한 한 시스템이 라이브로 산출**(설정값 존재·서명 레코드·활성 카탈로그·결재 상태 등). 산출 불가한 인간 판단(예: 검사실 실값 확정)은 명시적 서명 레코드로.

### 5.2 통합 정보구조(IA) — 4대 관리 축

콘솔을 4축으로 구성하고, 각 축 아래 정의 항목을 배치한다:

| 축 | 정의 항목(예) | 재사용 편집 화면 |
|---|---|---|
| **① 기준정보 정의** | 검사·참고치·패널·QC목표·코드매핑 / 코드셋(AST·감염병·병리·ICD-O·변이근거) / 용어·SNOMED / 바코드 | master · catalogs · terminology · barcode |
| **② 거버넌스·승인** | 조직 결재 A-1/A-2/A-3 / 검사실 실값 서명(참고치·QC·EDI·델타·병리·ACMG) / 반사검사 프로토콜 승인 | gates(+서명워크시트) · reflex |
| **③ 운영 설정·계정** | 위험치 채널·보존기간·상향간격 / 데이터 수명주기 / 계정·역할·Provider | settings · lifecycle · users |
| **④ 연동·정산** | HIS/PACS 연계·Reflex / ERP 청구 전송 | integration · billing |

### 5.3 `운영 관리 콘솔` 설계 (개시 준비도 확장)

현 `/admin/readiness`를 **정의 항목 레지스트리 기반 콘솔**로 확장:

- **정의 항목 레지스트리** (신규 `ManagementItem` 개념 — 코드 상수 or 경량 테이블):
  `{ key, axis(①~④), label, owner, lifecycle 산출식, fixHref, blocking(개시차단 여부) }`.
  준비도 8항목을 이 레지스트리로 일반화하고, 참고치·QC·코드셋·프로토콜 등으로 **확장**.
- **콘솔 화면** `/admin/console`(또는 readiness 승격):
  - 상단: 개시 차단(BLOCK) 요약 + 축별 진행률 도넛.
  - 축별 섹션: 각 정의 항목 카드(lifecycle 뱃지·담당·근거·**다음행동 버튼→편집 화면**).
  - 필터: 개시차단만 / 축별 / 담당별.
  - **워크플로우 뷰**(개시 전 모드): UNDEFINED→...→LIVE 파이프라인으로 항목을 늘어놓아 "무엇이 어느 단계에 걸려있나" 시각화.
- **통합 이력** — 결재·서명·반입·설정변경 이벤트를 항목별 타임라인으로(각 화면의 기존 이력 소스 집계).

### 5.4 기존 화면 매핑·재사용

- 편집·상세는 **기존 화면 그대로** 재사용(콘솔은 진입점·상태 집계 레이어). `signoff→gates 탭` 통합 선례를 따라, **개념 중복만 정리**:
  - `서명 워크시트`는 이미 gates 탭 → ② 거버넌스에 편입.
  - `master`·`catalogs`·`terminology`·`barcode`는 ① 기준정보로 그룹.
- 사이드바 `관리` 그룹은 **콘솔을 최상단 진입점**으로 두고, 개별 화면은 콘솔에서 딥링크(사이드바 축소 여지).

## 6. 단계별 구현 계획

| Phase | 범위 | 산출물 | 규모 |
|---|---|---|---|
| **P1 (레지스트리·콘솔 인덱스)** | 정의 항목 레지스트리(준비도 8→확장)·`/admin/console` 축별 카드·다음행동 링크·개시차단 요약 | 콘솔 화면 + `GET /admin/console`(readiness 일반화) | 소~중 |
| **P2 (lifecycle 표준화)** | 항목별 lifecycle 산출식 통일(설정존재·서명레코드·활성카탈로그·결재상태)·SEED/대표값 구별·재검토 플래그 통합 | 항목별 상태 산출 + 워크플로우 뷰 | 중 |
| **P3 (이력 통합·중복 정리)** | 결재·서명·반입·설정 이력 항목별 타임라인 집계·개념 중복 화면 탭 통합·사이드바 재편 | 통합 이력 뷰 + IA 정리 | 중 |

- **P1이 즉시 실익**: 준비도 대시보드를 정의 항목 전체로 일반화 + 축별 구조 → "한곳" 목표의 80%.
- P2/P3는 점진(각 화면 유지하며 상태·이력만 표준화).

## 7. 리스크·비범위·측정지표

**리스크**
- 상태 산출식이 화면 실데이터와 어긋나면 콘솔이 잘못된 GREEN을 보일 수 있음 → **라이브 산출 우선, 인간판단은 명시 서명**. (준비도의 SEED/플레이스홀더 감지 원칙 계승)
- 과도한 통합으로 기존 화면 회귀 → **비파괴 원칙**(편집 화면 재사용), 회귀 가드(nav coverage 등) 유지.

**비범위**
- 외부 입력값 자체(부서 URL·실 수가코드·조직 결재문서)는 콘솔로 대체 불가 — **추적·안내만**.
- 실 인프라(AWS·백업 경로)는 콘솔이 설정 여부만 표시.

**측정지표**
- 개시 준비 항목의 상태 가시성: 콘솔 1화면에서 정의 항목 N개의 lifecycle·담당·다음행동 확인 가능.
- 진입 클릭 수 감소: 관리 작업당 평균 화면 이동 횟수.
- 개시 차단 항목 오탐 0(SEED/대표값 구별).

## 부록 A. 정의 항목 → lifecycle 산출 예시

| 항목 | 산출식(라이브) | SIGNED/LIVE 조건 |
|---|---|---|
| 위험치 채널 | settings.CRITICAL_WEBHOOK_URL 존재·https·SEED패턴 | 실 URL·테스트발송 성공 |
| 조직 결재 A-x | org_approval.status·approver(데모=플레이스홀더) | 비데모 결재자·문서번호 |
| 검사실 실값 서명 | 서명 레코드(signoff) 존재 여부 | 항목별 서명 완료 |
| 코드셋(AST 등) | catalog_version status=ACTIVE | 실 코드북 반입·활성 |
| 참고치/QC/EDI | 커버리지·대표값 여부 | 검사실 서명 |
| 반사검사 프로토콜 | reflex_protocol status | ACTIVE(위원회 승인) |
| ERP 청구 | ERP_BILLING_URL·최근 ACCEPTED | 개통·정산 |
| 계정·Provider | 미연결 PHY/PAT 수 | 실계정 연결 |

> 이 산출식이 P1 레지스트리의 핵심. 준비도의 8개를 이 표로 확장하면 콘솔이 완성된다.
