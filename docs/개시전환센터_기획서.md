# 개시 전환 센터 — 기획서 (Go-Live Transition Center)

대상: 실 서비스 개시 **전환(단절점)** 에 필요한 체크리스트·근거문서·동의(승인)·키 입력·데이터 정리·시드 초기화를 **한 화면에서 순서대로 실행**하는 기능.

> **회귀 테스트 12건**으로 안전장치를 고정(E2E 465) — 4중 게이트·자동판정 차단·NA 사유·
> DOC_REQUIRED·sha256 무결성·PHI 미포함.
> **잔여: 없음**(다른 비가역 단계로의 게이트 확장은 필요 시점에).
>
> ⚠ **측정지표 정정**: "개시일 SSH 직접 실행 0건"은 **2건까지만** 달성된다 —
> HIS/PACS 운영 자격은 설정 허용목록 밖(`.env`)이고, `NEXT_PUBLIC_DEMO`는

> 이하는 그 근거가 된 원 기획이다.

> **한 줄 목적** — 지금 개시일 작업은 *문서를 보며 사람이 SSH로 스크립트를 돌리는* 방식이다.
> 그중 상당수가 **비가역**(파일럿 정리·데모계정 폐기·실 데이터 유입)인데, 실행 게이트도 감사 기록도
> 화면 밖에 있다. 이 기획은 **비가역 작업을 화면 안으로 들여와 게이트·근거·감사와 함께** 돌게 한다.

## 0. 왜 지금인가 — 이 기획이 막으려는 사고

2026-07-30 실측에서 **"화면상 완료로 보이지만 실제로는 아닌" 상태가 3건** 확인됐다.

| 화면 표시 | 실제 | 무엇을 놓칠 뻔했나 |
|---|---|---|
| `CRITICAL_WEBHOOK_URL` **설정됨** | 파일럿 시드 sink(`/_seed/…`) — 코드에 없는 경로 | 위험치 통보가 **전부 실패**하는데 완료로 오인 |
| 조직 게이트 4건 **APPROVED** | A-1 기입자 `U00`(데모), 나머지 3건 기입자 공백 | 실결재 0/3인데 승인된 것으로 오인 |
| 서명 워크시트 존재 | `signoff_record` **0건** | 참고치·QC가 전부 대표값인 채 개시 |

콘솔이 `SEED`/`BLOCK`으로 구분해 주고는 있으나, **판정이 여러 화면에 흩어져 있어 종합 판단은 결국 사람이 문서를 대조**해야 한다. 여기에 개시일에는 다음이 겹친다.

- `pilot-cleanup.sql`을 **psql로 직접** 실행 — 79줄 파괴적 SQL, 화면·감사·2인 확인 없음
- 실 환자 데이터가 이미 들어온 뒤 실행하면 **전량 소실**(스크립트 주석의 경고가 유일한 방어)
- 데모 계정 폐기·`NEXT_PUBLIC_DEMO` 플립·자격 컷오버가 각각 다른 화면·`.env`·재빌드
- v1.54.0에서 드러난 것 — **위험치 채널 값을 넣는 순간** E2E가 실 채널로 발신할 수 있었다(현재는 차단됐으나, 확인은 여전히 사람의 절차)

> **핵심 문제 진술**
> 개시 전환은 **일회성·비가역·순서 의존**인데, 지금은 그 절차가 **문서(3종)·SQL 스크립트·SSH·여러 관리 화면**에 분산돼 있다. 한 곳이라도 건너뛰면 임상 안전(위험치 미통보)이나 데이터 소실로 직결된다.

## 2. 목표·비목표

**목표**
1. 개시 전환에 필요한 전부를 **단일 화면**(`/admin/golive`)에서 순서대로 수행한다.
2. **비가역 작업은 게이트를 통과해야만** 실행된다 — 백업·드라이런·2인 승인·확인문구.
3. 모든 실행이 **감사 체인**에 남고, 근거 문서가 **시스템 안에** 보관된다.
4. 시드·파일럿 산출물을 **표식으로 정확히 식별**해, 실 데이터를 건드리지 않고 되돌린다.

5. **패키지 배포를 전제로 자리를 남긴다** — 향후 사이트 단위 배포 시 이 절차가 **신규 사이트 온보딩 기능**이 된다(§6). 기능은 지금 만들지 않되, 소급 복원이 불가능한 것(사이트 식별자·시드 표식·이름 규약)은 지금 넣는다.

**비목표**
- 운영단계(개시 후) 일상 운영 — `실서비스_운영단계_정의서.md` §4~§9 소관.
- AWS 인프라 구축(H6~H10) 자동화 — 인프라팀 수작업 영역.
- 조직 결재 자체의 전자결재화 — 병원 EAS 소관(LIS는 참조·기입만).
- **다중 사이트 중앙 관리·원격 배포·라이선스 검증** — §6.3에서 미루기로 판단(내보내기로 대체).

## 3. 설계

### 3.1 정보구조 — 한 화면 4탭

```
/admin/golive  개시 전환 센터                      [진행률 12/34 · 차단 4]
├── ① 준비도 체크리스트   무엇이 남았나 (A~H + 잔여 12건을 항목화)
├── ② 근거 문서함         결재·회신·서명 원본 첨부 (항목에 결속)
├── ③ 전환 실행           런시트 단계별 실행 (비가역 게이트)
└── ④ 최종 승인           GO/NO-GO (기존 golive_approval 승격)
```

**콘솔과의 관계 — 중복이 아니다.** `/admin/console`은 *상시* 관리 항목의 **정의 상태**를 본다(운영 중에도 쓴다). `/admin/golive`는 *일회성* 전환 **절차의 실행**을 본다. 콘솔 5축 항목은 체크리스트가 **참조**하며(자동 판정 소스), 중복 기재하지 않는다.

### 3.2 ① 준비도 체크리스트

문서 3종의 항목을 **하나의 레지스트리**로 승격한다(`decision-registry.ts` 패턴 재사용).

```ts
export interface GoLiveTask {
  code: string;              // 'A2', 'C1', 'D1', 'RUN-6' …
  phase: 'PREP' | 'CUTOVER' | 'POST';   // 준비 / 전환당일 / 직후검증
  group: string;             // '구성 토글' | '자격증명' | '데이터·마스터' | '조직 게이트' …
  title: string;
  owner: string;             // 부서
  blocking: boolean;         // 미완이면 개시 승인 불가
  evidence: 'NONE' | 'DOC' | 'DOC_REQUIRED';  // 근거 문서 첨부 요구 수준
  autoCheck?: string;        // 자동 판정 키(콘솔 readiness check key 재사용)
  irreversible?: boolean;    // ③ 전환 실행 대상
  dependsOn?: string[];      // 선행 항목(순서 강제)
  docRef?: string;           // 정본 문서 경로
  requires?: SiteCapability[];  // 사이트 능력 조건 — 없으면 항목 자체가 생성되지 않는다(§6.2a)
  deprecated?: boolean;      // 삭제 대신 표시 — 과거 승인 스냅샷 해석 보존(§6.4)
}
```

- **자동 판정 우선**: `autoCheck`가 있으면 시스템이 판정하고 사람이 못 바꾼다(위험치 채널·게이트 실결재·서명 섹션·데모계정 등 — 이미 `readiness()`가 계산 중). **"화면상 완료" 오인의 근본 차단**이다.
- **수동 항목**은 담당자가 완료 처리하되 `evidence: DOC_REQUIRED`면 **첨부 없이는 완료 불가**.
- `dependsOn`으로 순서를 강제한다(예: `H1 법무` → `H5 RDS`, `A-3 결재` → `자격 컷오버`).

| 신규 테이블 | 용도 |
|---|---|
| `golive_task_record` | code · status(OPEN/DONE/NA) · owner · completedBy · completedDt · note · naReason |

> ⚠ **`NA`(해당없음) 처리에는 사유가 필수**다. 개시 압박에서 항목을 조용히 지우는 것이 가장 흔한 우회 경로다.

### 3.3 ② 근거 문서함

`org_approval.docNo`(문자열)만으로는 **결재가 실재했는지 소명할 수 없다.**

```ts
// 신규: golive_attachment
{ attachmentId, taskCode?, gateCode?, signoffSection?, decisionKey?,   // 무엇에 붙는가
  filename, mimeType, sizeBytes, data(Bytes), sha256,                   // 원본 + 무결성
  category: 'APPROVAL'|'REPLY'|'SIGNOFF'|'LEGAL'|'EVIDENCE',
  uploadedBy, uploadedDt }
```

- **기존 첨부 인프라 재사용**: `ResultAttachment`의 MIME 화이트리스트(PDF/PNG/JPEG/WEBP)·20MB 상한·`nosniff`·파일명 정규화·서비스단 소유 재검증 패턴을 그대로 가져온다(임상 첨부와 **테이블은 분리** — 보존정책·권한이 다르다).
- **sha256 기록**: 첨부 후 교체 여부를 탐지한다(서명 워크시트의 스냅샷 해시와 같은 발상).
- 권한: 업로드 `ADM`, 열람 `ADM`·`AUD`. **감사 대응 시 이 문서함이 1차 증빙**이 된다.

### 3.4 ③ 전환 실행 — 비가역 작업의 게이트

컷오버 런시트 단계를 **실행 가능한 단계**로 만든다. 각 단계는 동일한 4중 게이트를 통과한다.

```
[선행조건] → [드라이런] → [2인 승인] → [확인문구 입력] → 실행 → [사후 스냅샷]
```

| 게이트 | 내용 | 근거 |
|---|---|---|
| **선행조건** | ① 최근 24h 내 백업 존재 ② 복구 리허설 최근 통과 ③ 선행 task 완료 | 되돌릴 지점이 없으면 비가역 작업을 시작하지 않는다 |
| **드라이런 필수** | 삭제·변경 대상 **건수를 테이블별로** 먼저 보여준다. 드라이런 없이 실행 불가 | `pilot-cleanup.sql` ①블록이 이미 하는 일을 API로 |
| **2인 승인** | 요청자 ≠ 승인자(ADM 2명). 수혈 2인 확인·결과 자가검증 차단과 **같은 직무분리 패턴** | 개시일 단독 조작 차단 |
| **확인문구** | 대상 건수를 포함한 문구를 타이핑(`파일럿 데이터 1,284건 삭제`) | 오클릭 방지 |
| **사후 스냅샷** | 전/후 건수·소요·실행자를 `cutover_run`에 기록 + 감사 체인 append | "무엇이 지워졌나"를 나중에 답할 수 있어야 한다 |

**🔴 최상위 안전장치 — 실 환자 데이터 감지 시 하드 차단**

```
if (실_환자_데이터_존재) → 정리 API는 409로 거부. override 불가.
```

판정: `patient.hisPatientUuid IS NOT NULL` 또는 `lab_order.orderSource='HIS'` 중 **시드 표식이 없는** 레코드가 1건이라도 있으면 실 유입으로 본다. 현재 스크립트는 이 판정 없이 테이블을 통째로 지우며, 주석 경고가 유일한 방어다. **이 가드 하나가 이 기획의 가장 큰 값**이다.

| 신규 테이블 | 용도 |
|---|---|
| `cutover_run` | runId · step · mode(DRY/EXEC) · requestedBy · approvedBy · beforeJson · afterJson · startedDt · finishedDt · result |

### 3.5 ④ 시드·파일럿 데이터 정리 — 표식 기반으로 전환

**현재의 위험**: `pilot-cleanup.sql`은 `DELETE FROM <표>` 전량 삭제다. 실 데이터가 섞이면 구분할 방법이 없다.

**제안**: 시드·파일럿 산출물에 **표식**을 남긴다.

```prisma
model SeedArtifact {          // 신규 — 시드가 만든 것의 등록부
  artifactId  String @id
  batch       String          // ★4종 규약 고정(§6.2c): product-demo | site-starter | site-pilot | e2e
  entity      String          // 'patient' | 'lab_order' | …
  pk          String          // 대상 PK
  createdDt   DateTime @default(now())
  @@index([batch]); @@index([entity, pk])
}
```

> **`batch`를 자유 문자열로 두지 않는다(§6.2c).** 패키지 배포가 되면 시드는 3종으로 갈라지고
> (제품 데모 / 사이트 스타터셋 / 현장 파일럿), **지울 것과 남길 것이 배치로 구분**된다.
> 이름 규약이 없으면 "스타터셋 마스터"를 파일럿 데이터와 함께 지우게 된다.

- 시드 스크립트(`prisma/seed*.ts`)·리허설 스크립트가 **생성 시점에 등록**한다.
- 정리는 `SeedArtifact` 기준 **선택 삭제** — 실 데이터는 구조적으로 대상이 되지 않는다.
- 등록되지 않은 과거 파일럿 데이터는 **1회 백필**(현행 휴리스틱 `T-`·`U00~U08`·`_seed`로 등록만 하고 삭제는 하지 않음 → 사람이 목록 확인 후 승인).
- 마스터 대표값도 같은 방식 — `seed-signoff` 배치로 등록해 두면, **서명 실값 반영 시 "무엇이 아직 대표값인가"를 정확히 답할 수 있다**(지금은 `signoff_record` 유무로 섹션 단위 추정).

**시드 초기화 시나리오 3종**
| 시나리오 | 대상 | 게이트 |
|---|---|---|
| 파일럿 트랜잭션 정리 | `batch in (seed-demo, pilot-rehearsal)` 트랜잭션 | 전체 4중 게이트 + 실데이터 하드 차단 |
| 데모 계정 폐기 | `U00~U08` | 2인 승인 · **최후 관리자 보호**(기존 users 가드 재사용) |
| 마스터 대표값 → 실값 | `seed-signoff` 배치 | 서명 완료 섹션만 교체 허용(미서명 교체 차단) |

### 3.6 키 입력 — 개시 키 묶음 뷰

`/admin/settings`는 **전체 설정** 화면이라 개시에 필요한 키가 묻힌다. 전환 센터에는 **개시 필수 키만** 순서대로 노출한다(설정의 저장 로직·검증·감사는 그대로 재사용, 화면만 추가).

| 키 | 게이트 |
|---|---|
| `CRITICAL_WEBHOOK_URL` + `_SECRET` | https 강제 · **테스트 발송 성공해야 완료 처리** · 시드 sink 패턴이면 `SEED`로 표시 |
| `OPS_WEBHOOK_URL` | 테스트 발송 |
| `LIS_BACKUP_OFFSITE` | 경로 쓰기 가능 확인 |
| HIS/PACS 운영 자격 | A-3 결재 선행(`dependsOn`) · 주입 후 **왕복 스모크 통과** |

> ⚠ **v1.54.0 교훈을 항목으로 못박는다.** 위험치 채널 값을 넣은 직후 **E2E 재실행으로 발신 0 확인**을 체크리스트 `POST` 항목(`RUN-9`)으로 둔다. 코드로는 이미 차단했지만(웹훅 env 언셋), 값 주입 시점이 유일한 발현 시점이라 절차로도 확인한다.

### 3.7 ④ 최종 승인

기존 `golive_approval`을 그대로 쓰되, 승인 조건을 **체크리스트 기준**으로 바꾼다.

- `blocking && status != DONE` 인 task가 0이어야 GO 가능
- 잔존 시 **override + 잔여위험 기술 + 스냅샷**(현행 유지)
- 승인 시 **그 시점 체크리스트 전문을 JSON 스냅샷**으로 보존 — "무엇을 확인하고 승인했는가"가 남는다
- 승인 후 blocking 재발생 시 `APPROVED_STALE`(현행 로직 재사용)

## 6. 배포 형태 — 사이트별 단독 설치 (확정)

> **✅ 결정(2026-07-30, 사용자 확정): LIS는 패키지 형태로 사이트마다 단독 설치한다.**
> **멀티테넌트(공유 DB·행 단위 격리)는 채택하지 않는다.** 사이트 = 서버 = DB 1:1:1을 고정한다.
>
> 그러면 개시 전환은 *"우리 병원 1회"* 짜리 도구가 아니라 **신규 사이트마다 반복되는 제품 기능
> (온보딩)** 이 된다. §1~§5의 설계는 그 전제 위에서 읽어야 한다.

### 6.0 왜 멀티테넌트로 가지 않는가 — 재논의 방지용 기록

검토 후 내린 결론이므로 근거를 남긴다. **아래 전제가 바뀌지 않는 한 다시 논의하지 않는다.**

**(1) 코드가 단일 인스턴스를 명시적으로 전제한다** — 이건 우연이 아니라 설계다.
- `audit-chain.service.ts` — 감사 해시체인이 **in-memory tail + 뮤텍스**, `seq` 전역 단조증가.
  주석에 "단일 인스턴스(lis-api 1) 전제"가 박혀 있다. 테넌트별 체인으로 쪼개면
  **tamper-evident 무결성 논증을 처음부터 다시** 해야 한다.
- `settings.service.ts` — 설정 캐시가 같은 전제(주석 명시).
- 크론 **11개**가 전역 실행. 채번(검체 `S+날짜`·병리 `SP-YYYY-`·`max+1`)도 전역.
- 레이트리밋 in-memory(C6에서 "단일 인스턴스라 충분"으로 결정 완료).
- → 행 단위 공유는 **사실상 재작성**이며, 그 대상이 하필 감사·채번 같은 소명 책임 영역이다.

**(2) 격리 실패의 결과가 다른 병원 환자정보 유출이다.** 2026-07-30 검토에서 단일 테넌트인데도
권한 격리 결함을 실제로 찾았다(알림함에 제제 회수 환자명단이 접수담당까지 노출). 50여 개 테이블
중 **하나만 테넌트 결속이 빠져도** 같은 유형의 실수가 교차 유출이 된다.

**(3) 복구 단위가 곧 계약 단위다.** 공유 DB에서는 병원 A의 복구가 병원 B를 함께 롤백시킨다.
`docs/백업복구_운영절차서.md`의 RPO/RTO가 사이트 단위로 설계돼 있고, 이를 테넌트별로 만들려면
결국 물리 분리로 되돌아온다.

**(4) 병원마다 업그레이드 승인 시점이 다르다.** 의료기관 변경관리 규정상 한 사이트가 변경 동결을
선언하면 단일 인스턴스에서는 **전 사이트가 묶인다.** 실무적으로 가장 큰 장벽이다.

**(5) 격리 증명 요구.** 인증·실사에서 물리적 분리를 계약서에 명시하라는 요구가 흔하다.
"DB가 분리돼 있다"는 방어 가능하지만 "애플리케이션이 걸러준다"는 방어하기 어렵다.

> **재검토 트리거(이 셋이 동시에 성립할 때만):** 사이트 20개 초과 · 운영 인력이 실제 병목 ·
> 고객이 공유 DB를 계약상 수용. 그전까지 운영 비용 문제는 **배포 자동화와 중앙 관측**으로 푼다
> (멀티테넌시보다 싸고 위험이 없다).
>
> ⚠ 타깃 고객군이 종합병원에서 **의원·소규모 검사센터로 바뀌면 전제가 달라진다** — 격리 요구가
> 약하고 단가 민감도가 높아 계산이 뒤집힐 수 있다. 그때는 (1)의 기술 부채부터 다시 계산할 것.

### 6.0-b 이 결정이 확정하는 것

| 항목 | 확정 내용 |
|---|---|
| 배포 단위 | **사이트 = 서버 = DB (1:1:1)** — 컨테이너 세트를 사이트마다 독립 기동 |
| 앱 인스턴스 | **사이트당 1개**(다중 인스턴스는 S6 선행개발 필요 — `docs/선행개발_명세_S1-S6.md`) |
| 데이터 격리 | **물리 격리**. 애플리케이션 레벨 테넌트 필터를 도입하지 않는다 |
| `siteCode` 용도 | 테넌트 격리가 **아니라** 배포 식별·승인 기록 결속·준비도 내보내기용 |
| 백업·복구 | 사이트 단위. 타 사이트 영향 없음(현행 유지) |
| 업그레이드 | 사이트별 독립 — 사이트마다 다른 버전이 정상 상태(§6.4) |

### 6.1 무엇이 달라지는가

| 관점 | 단일 사이트(현재 가정) | 패키지·다중 사이트 |
|---|---|---|
| 체크리스트 | 우리 병원 34항목 고정 | **사이트마다 다르다** — PACS 미사용·ERP 미연동·병리 미운영 병원이 존재 |
| 시드 | 파일럿 합성 데이터 1종 | **3종** — ①제품 데모(평가·교육) ②사이트 초기 마스터(스타터셋) ③현장 파일럿 |
| 근거 문서 | 우리 병원 결재철 | **사이트별 규제 증빙 보관소** — 실사·인증 시 사이트 단위로 제출 |
| 버전 | 서버 1대 = 1버전 | **사이트마다 다른 버전**이 돌아간다 |
| 준비도 확인 | 구축팀이 직접 접속 | **원격 접속 불가 전제**(의료 데이터·폐쇄망) → 내보내기로 검수 |
| 설정 | `.env` + DB 설정 | **패키지 기본값 / 사이트 프로파일 / 운영자 입력** 3계층 |

### 6.2 지금 결정해야 하는 것 — 나중에 바꾸면 비싼 것

**(a) 체크리스트 레지스트리에 프로파일 조건을 넣는다**

항목을 상수 배열로 하드코딩하면, 사이트마다 "해당 없음"을 손으로 `NA` 처리하게 된다 — §3.2에서 경계한 *조용한 우회*가 제품 기본 동작이 되어 버린다.

```ts
export interface GoLiveTask {
  // …기존 필드
  requires?: SiteCapability[];   // ['PACS'] · ['ERP'] · ['PATHOLOGY'] · ['GENOMIC']
}
// 사이트 프로파일에 해당 능력이 없으면 항목이 **애초에 생성되지 않는다**(NA 처리가 아니라 비해당).
```

`SiteProfile`(신규, 1행): `siteCode` · `siteName` · `capabilities[]` · `deployedVersion` · `installedDt`.
현 서버는 전 capability를 켠 프로파일 1행으로 백필하면 동작이 동일하다 — **지금 넣으면 비용 거의 0, 나중이면 레지스트리·기록·화면을 모두 손봐야 한다.**

**(b) 사이트 식별자를 승인·감사 기록에 결속한다**

`golive_approval` · `golive_task_record` · `cutover_run` · `golive_attachment`에 `siteCode`를 남긴다. 사이트가 여럿이 되면 **"이 승인이 어느 사이트 것인가"** 를 나중에 복원할 수 없다(백업 파일이 섞이는 순간 끝난다). 컬럼 하나를 지금 넣는 비용과, 나중에 마이그레이션으로 추정 복원하는 비용은 비교가 안 된다.

> ⚠ **`siteCode`는 테넌트 격리 장치가 아니다**(§6.0-b). DB가 이미 사이트별로 분리돼 있으므로
> 쿼리 필터로 쓰지 않는다. 용도는 **배포 식별·승인 기록 결속·내보내기 라벨** 뿐이다.
> 이걸 격리용으로 오해해 쿼리에 끼워 넣기 시작하면 채택하지 않기로 한 L3로 흘러간다.

**(c) 시드 배치 이름을 규약으로 고정한다**

§3.5의 `SeedArtifact.batch`를 **자유 문자열로 두지 않는다.**

| 배치 | 성격 | 개시 시 처리 |
|---|---|---|
| `product-demo` | 제품 데모·교육용(패키지 동봉) | **전량 삭제** |
| `site-starter` | 사이트 초기 마스터(코드 스타터셋·기본 참고치) | **보존**하되 서명 실값으로 교체 대상 |
| `site-pilot` | 현장 파일럿·리허설 산출물 | **전량 삭제** |
| `e2e` | 테스트 전용(운영 DB에 있으면 안 됨) | 발견 시 **경고** |

이 구분이 없으면 "지워야 할 시드"와 "남겨야 할 스타터셋"을 구분할 수 없다. **§3.5의 값이 절반으로 준다.**

**(d) 설정 3계층을 명시한다**

현재는 `코드 기본값 → env → DB 설정`이다. 패키지에서는 **사이트 프로파일**이 하나 더 들어간다.

```
패키지 기본값(코드)  <  사이트 프로파일(설치 시 확정)  <  env(배포)  <  DB 설정(운영자 화면)
```

⚠ **패키지에 시크릿 기본값을 절대 넣지 않는다.** 현행 `SEED_PASSWORD` 미설정 시 무작위 생성 패턴(`prisma/seed.ts`)이 정답이고, 이를 **전 시크릿에 확대**한다. 패키지에 고정 기본 시크릿이 들어가면 전 사이트가 같은 값을 쓰게 된다 — 한 사이트 유출이 전 사이트 침해가 된다.

**(e) 준비도 내보내기(서명된 스냅샷)**

원격 접속 없이 구축팀·본사가 사이트 준비도를 검수할 수 있어야 한다.

- `GET /admin/golive/export` → 체크리스트 전문 + 자동판정 근거 + 첨부 **목록**(원본 아님) + 사이트/버전 + **해시 서명** JSON
- **PHI는 절대 포함하지 않는다** — 건수·상태·판정 근거만. 첨부 원본은 사이트에 남는다.
- 이건 §3.7 최종 승인의 스냅샷을 **파일로 꺼내는 것**이라 추가 비용이 작다.

### 6.3 미뤄도 되는 것

| 항목 | 미루는 이유 |
|---|---|
| 중앙 관리 콘솔(본사에서 전 사이트 취합) | 사이트가 여럿이 된 뒤 실제 운영 요구를 보고 만들어야 한다. 내보내기(6.2e)가 있으면 그때까지 수동 취합으로 충분 |
| 원격 업데이트·자동 배포 | 의료기관 변경관리 규정상 **사이트 승인 없는 자동 배포는 불가**한 경우가 많다. 규정 확인이 선행 |
| 라이선스 키 검증 | `LICENSE`(독점) 법무 검토 중(결정 등록 `license_legal`). 검토 결과에 따라 방식이 달라진다 |
| ~~멀티테넌시~~ | **미루는 것이 아니라 채택하지 않기로 확정** — §6.0 참조 |

### 6.4 업그레이드 시 체크리스트 정합

사이트마다 버전이 다르면 **레지스트리 항목도 버전마다 다르다.** 규칙을 미리 정한다.

- 항목은 **추가만 하고 삭제하지 않는다**(`deprecated: true`로 표시). 삭제하면 과거 승인 스냅샷의 항목을 해석할 수 없다.
- 업그레이드로 신규 blocking 항목이 들어오면, **이미 승인(GO)된 사이트는 `APPROVED_STALE`로 전환**하고 운영자에게 알린다(현행 로직 재사용). 조용히 통과시키지 않는다.
- 승인 스냅샷에 `registryVersion`을 함께 저장한다.

### 6.5 구현 계획 반영

§4의 계획에 다음을 **P1·P3에 흡수**한다(별도 단계로 늘리지 않는다 — 지금 넣으면 거의 공짜다).

| 반영 | 흡수 위치 | 추가 비용 |
|---|---|---|
| `SiteProfile` 1행 + `requires` 필드 | **P1** | 소 |
| `siteCode` 컬럼(4개 테이블) | **P1·P3·P4** 신설 시 함께 | 거의 0 |
| 시드 배치 4종 규약 | **P3** | 0 (이름 고정만) |
| 시크릿 기본값 금지 원칙 | **P3**(시드 스크립트 손볼 때) | 소 |
| 준비도 내보내기 | **P5** | 소 |

> **원칙: 다중 사이트 "기능"은 지금 만들지 않되, 나중에 만들 수 있는 "자리"는 지금 남긴다.**
> 컬럼·필드·이름 규약은 지금이 가장 싸고, 승인 기록·시드 표식은 **소급 복원이 불가능**하다.
