## S1. 논리 백업 → S3 · GPG 암호화

**왜** — 현재 백업은 로컬 1곳뿐이다. 인스턴스가 소실되면 전량 유실된다. 단일 노드 구성에서
백업은 유일한 복구 수단이므로, 백업이 서버와 같은 운명을 공유해서는 안 된다.

**무엇** — 코드는 이미 완료돼 있다(`infra/scripts/backup.sh`). **환경변수 설정과 키 관리만** 남았다.

**어떻게**
1. GPG 키쌍 생성 → 공개키만 서버에, **개인키는 오프라인 보관**(금고·별도 매체)
2. **S3 버킷**(ap-northeast-2, 퍼블릭 차단, KMS 암호화, 버전관리, 교차 리전 복제 금지)
3. EC2 인스턴스 프로파일에 **해당 버킷만** 권한 부여
4. `.env`에 `LIS_BACKUP_GPG_RECIPIENT`, `LIS_BACKUP_OFFSITE=s3://…` 설정
5. 크론 1회 수동 실행 후 S3 도착·복호화 확인

**완료 조건**
- S3 버킷에 당일 백업이 `.gpg`로 존재
- `gpg -d <파일> | gunzip | head` 가 정상 출력(복호화 가능 확인)
- 개인키 보관 위치·담당자가 문서화됨(키를 잃으면 백업은 영구히 열 수 없다)

**주의**
- 개인키를 서버에 두면 오프사이트의 의미가 없다. 서버가 털리면 백업도 함께 털린다.
- RDS 스냅샷이 있어도 **논리 백업은 별도로 필요**하다. 스냅샷은 AWS에 종속되어 계정 사고·사업자
  이슈 시 열 수 없다. 사업자와 무관하게 여는 사본이 S1의 목적이다.

## S2. RDS 자동백업 · PITR 설정·검증

**왜** — 일 1회 백업만으로는 최대 24시간 손실이다(RPO 24h). 목표는 5분.
공용 서버에서는 postgres 설정 변경이 불가해 보류됐던 체크리스트 **C2 잔여** 항목이다.

**AWS로 오면서 달라진 점** — 직접 WAL 아카이빙을 구현할 필요가 **없다.**
RDS 자동백업을 켜면 PITR이 함께 제공된다. **구현이 아니라 설정·검증 과제**로 축소됐다.

**어떻게** — [백업복구_운영절차서.md](백업복구_운영절차서.md) §2.
- 자동백업 보존 14일, 백업창 새벽, **저장 암호화(생성 시에만 설정 가능)**, 삭제 방지 활성

**완료 조건**
- `LatestRestorableTime`이 현재에서 5분 이내로 유지됨 → **CloudWatch 알람 연결**
- **PITR 복구 리허설 1회 성공**(임의 시점으로 별도 인스턴스 복원 → 데이터 확인)
- 복원 후 `/audit/verify`가 `ok:true`

**주의**
- **RDS 저장 암호화는 생성 시에만 켤 수 있다.** 나중에 켜려면 스냅샷 복원으로 새 인스턴스를
  만들어야 하므로, 처음 생성할 때 반드시 활성화한다.
- 자동백업 보존 기간이 곧 PITR 가능 범위다. 14일보다 긴 시점으로는 돌아갈 수 없다.

## S3. 블루그린 green 크론 비활성

**왜** — `deploy-bluegreen.sh`는 green(4102)을 blue와 **동시에** 띄운다. 이 구간에서 양쪽의 크론
8종이 함께 돈다.

| 크론 | 파일 | 중복 시 증상 |
|---|---|---|
| HIS 오더 폴링(5분) | `integration.service.ts` | 동일 오더 중복 처리 시도(멱등키로 차단되나 오류 로그) |
| Reflex 폴링·재시도(5·10분) | 〃 | 중복 발신 시도 |
| 위험치 재발송(3분)·에스컬레이션(5분) | `critical-notifier.service.ts` | **중복 통보 발송 가능** |
| 연계 감시(10분) | `integration-health.service.ts` | 중복 알림 |
| 보존 정리(일 04:00) | `lifecycle.service.ts` | 중복 삭제 시도 |
| 근접만료 알림(일 08:00) | `transfusion.service.ts` | 중복 알림 |

멱등키 덕분에 데이터 오염은 막히지만, **위험치 중복 통보**는 임상 현장에 혼선을 준다.

**무엇** — `CRON_DISABLED=on`(가칭) 환경변수를 도입해 green 부팅 시 크론을 건너뛴다.

**어떻게**
1. `app.module.ts` 또는 각 서비스에 공통 가드 추가 — `ScheduleModule` 등록을 조건부로 하거나,
   각 `@Cron` 핸들러 선두에서 `if (process.env.CRON_DISABLED === 'on') return;`
   (전자가 깔끔하나 후자가 변경 범위가 작다)
2. `docker-compose.prod.yml` api `environment:`에 `CRON_DISABLED: ${CRON_DISABLED:-}` 등재
   — **`check-compose-env.sh`가 미배선을 잡으므로 빠뜨릴 수 없다**
3. `deploy-bluegreen.sh`의 green 파생 env 파일에 `CRON_DISABLED=on` 추가
4. nginx 전환 후 blue를 내리고 green을 정식 기동할 때는 이 값 없이 재기동

**완료 조건** — 블루그린 전환 중 green 로그에 크론 실행 기록이 없고, blue만 정상 수행.

**주의** — `process.env.X === 'on'` 형태로 비교할 것. compose는 미설정 env를 **빈 문자열**로
전달하므로 `??` 기본값 패턴은 쓰지 않는다(`trustProxyHops` 사고 전례 — `common/trust-proxy.ts` 주석 참조).

## S4. DB 소유자/앱 계정 분리

**왜** — 현재 앱이 쓰는 `lis` 계정이 테이블 **소유자**다. 소유자는 `ALTER TABLE ... DISABLE TRIGGER`가
가능하므로, 앱 계정이 탈취되면 `audit_log` UPDATE 차단 트리거를 스스로 끌 수 있다. 감사 무결성의
마지막 방벽이 앱 권한과 같은 등급인 셈이다.

**무엇** — 소유자(마이그레이션 전용)와 앱 계정(런타임)을 분리하고, 앱 계정에서 위험 권한을 회수.

**어떻게**
1. 소유자 역할 `lis_owner` 생성 — 마이그레이션·DDL 전용
2. 앱 계정 `lis_app` — `SELECT/INSERT/UPDATE/DELETE`만, DDL·TRIGGER 권한 없음
3. `audit_log`에 대해 `lis_app`의 **DELETE도 회수**(보존 정리는 별도 배치 계정으로)
4. `DATABASE_URL`은 `lis_app`, 마이그레이션 실행 시에만 `lis_owner`
   — 현재 api 컨테이너가 기동 시 `migrate deploy`를 수행하므로 **기동 흐름 변경이 따른다**
   (마이그레이션을 별도 one-shot 컨테이너로 분리하는 편이 깔끔 — 블루그린은 이미 그 구조)

**완료 조건**
- `lis_app`으로 `ALTER TABLE audit_log DISABLE TRIGGER ...` 시도 시 권한 오류
- `lis_app`으로 `DELETE FROM audit_log` 시도 시 권한 오류
- 정상 업무·마이그레이션·보존 정리는 모두 동작

**주의** — 기동 시 마이그레이션 구조를 바꾸는 작업이라 배포 절차와 맞물린다. 분리 이관과 함께 진행할 것.

## S5. 첨부를 S3로 분리

**왜** — `ResultAttachment.data`가 DB 안 `bytea`(≤20MB/건)라 **DB 볼륨 = 첨부 볼륨**이다.
사이징 추정에서 5년 70GB 중 55GB가 첨부였다. DB가 커지면 스냅샷·복원 시간(RTO)이 함께 늘어난다.

**착수 기준(AWS에서 상향)** — 원래는 "첨부가 DB 절반 초과 시"였으나, AWS에서는 **개시 시점에 함께
검토할 것을 권장**한다.
- S3 단가가 RDS 스토리지보다 훨씬 낮다
- RDS를 200GB → 50GB로 줄일 수 있어 **스냅샷·복원이 빨라진다(RTO 직결)**
- S3가 이미 백업용으로 구성돼 있어 추가 인프라가 없다

다만 **개시 일정과 검증 부담**을 함께 고려해 결정한다(설계 §10 D4).

**무엇** — 바이너리를 오브젝트 스토리지로 옮기고 DB에는 참조만 남긴다.

**어떻게**
1. 스키마: `data Bytes` → `storageKey String` (+ 체크섬·마이그레이션 기간 병행 컬럼)
   저장 위치는 **ap-northeast-2 버킷**, 서버측 암호화(KMS), 퍼블릭 차단
2. 업로드: 스토리지에 저장 후 키만 기록. **서버 경유 저장**(presigned 직접 업로드는 권한 검증이
   약해지므로 지양 — 현재 도메인별 권한 재검증 로직을 유지해야 한다)
3. 다운로드: 기존 권한 검증(`attachment-access.ts`) 후 **서버가 스트리밍**. presigned URL을 클라이언트에
   주면 URL 유출 시 권한 우회가 되고, 도메인별 격리 검증을 건너뛰게 된다
4. 이관 배치: 기존 bytea → 스토리지 이동 후 검증·삭제
5. 백업 범위 확장: 스토리지도 백업 대상(DB 백업만으로는 첨부가 복구되지 않는다)

**완료 조건** — 신규 업로드·다운로드·삭제가 스토리지 경유로 동작, 기존 첨부 전량 이관·검증,
백업/복구 절차서에 스토리지 항목 반영, 도메인별 권한 격리 E2E 통과.

**주의** — 이 변경은 **복구 절차를 바꾼다**. DB만 복원하면 첨부가 없는 상태가 되므로,
백업복구 절차서와 리허설을 반드시 함께 갱신할 것.

## S6. 감사체인 잠금·throttler 분산화 (HA 전환 시 **필수 선행**)

**왜** — 두 가지가 **in-memory**라 API를 2대 이상으로 늘리면 곧바로 깨진다.

| 구성요소 | 현재 | 다중 인스턴스 시 문제 |
|---|---|---|
| `AuditChainService` 직렬화 뮤텍스 | 프로세스 내 | 두 인스턴스가 동시에 append → `seq` 충돌·`prevHash` 링크 파손 → **감사 무결성 상실** |
| `AppThrottlerGuard` 저장소 | 프로세스 메모리 | 인스턴스별로 카운터가 나뉘어 실효 한도가 N배 |

감사 체인은 의무기록 신뢰성의 근거다. **이 작업 없이 API를 늘리는 것은 허용하지 않는다.**

**무엇**
1. 체인 append를 **DB 원자성**으로 이전 — 예: `SELECT ... FOR UPDATE`로 tail 행을 잠그고
   같은 트랜잭션에서 insert, 또는 PostgreSQL 어드바이저리 락(`pg_advisory_xact_lock`)
2. throttler 스토리지를 Redis로 — **ElastiCache**(공용 redis 불가침 제약은 분리로 해소)

**완료 조건**
- API 2인스턴스 동시 부하에서 `/audit/verify`가 `ok:true` 유지(동시 append 부하 테스트)
- 레이트리밋이 인스턴스 수와 무관하게 동일 한도로 동작
- 기존 단일 인스턴스 동작 무회귀(E2E 전량 통과)

**주의** — 어드바이저리 락은 **연결 단위**다. Prisma 커넥션 풀에서 트랜잭션 스코프 락
(`pg_advisory_xact_lock`)을 써야 커넥션 반환 시 자동 해제된다. 세션 락을 쓰면 풀에 남아 교착된다.

## 참고 · 이 명세를 읽을 때

- 각 항목의 **주의** 절은 실제로 밟았거나 밟을 뻔한 함정이다. 건너뛰지 말 것.
- 환경변수를 새로 추가하면 `docker-compose.prod.yml`의 `environment:`에도 **반드시** 등재한다.
  `.env`에만 넣으면 컨테이너에 전달되지 않는다(`check-compose-env.sh`가 CI에서 차단).
- 보안 기준선(`docs/보안_점검_2026-07-21.md`)의 방어는 회귀 금지 대상이다. 작업 중 걸리적거린다고
  풀지 말고, 필요하면 그 이유를 문서에 남기고 대안을 세울 것.
